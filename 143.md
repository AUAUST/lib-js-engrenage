# #143 config: layered registry with lazy sections

- State: OPEN
- Labels: 🚀 — Improvement

## Body

#137 · §Config pipeline

## Context

`createResolvedConfig` (`project/config`, 659 lines of nested closures) builds the aggregate `ResolvedConfig` and imports six tool domains: the last upward imports, marked `@debt`. Every definer, the CLI plumbing and `bin/engrenage/*` load the whole aggregate, so one invalid section blocks every tool. Decided: consumers keep `export default defineTsdownConfig()`, with no registry or resolver passed by hand.

## Steps

1. In `project/config`, resolve the project sections (global settings, structure, environments, presets, package, tsconfig, baseline, build) lazily through `get(section)`, memoized per section and root, replacing the temporary `get` of #146 (`OptionContext`, `src/foundation/options/types/`).
2. Give each tool domain's definer its own section resolution through `project/config`, reading lower sections through `get`.
3. Add `workflows/registry` with eager validation and the composed `Config` type; switch the CLI plumbing and `bin/engrenage/*` to its `loadConfig(root)`.
4. Compose each environment's schema from the domains' sub-schemas (`tsconfig`, `exports`, `define`).
5. Delete `createResolvedConfig`, `ResolvedConfig` and the `@debt` markers on the upward imports they caused.

## Tests

- A definer resolves while an unrelated section is invalid; eager validation of the same config fails on it, and on an unknown key.
- Two sections reading each other fail with the cycle path.

## Done when

No module imports a higher layer.
