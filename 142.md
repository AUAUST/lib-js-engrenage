# #142 config: role catalogue and contracts

- State: CLOSED
- Labels: 🚀 — Feature

## Body

Part of #137, under #158. Read the plan, its **Core model**, **Inside a domain** and **Roles** sections, before starting.

## Context

Engrenage has no notion of roles: directories such as `utils/`, `types/`, `setup/` and `config/` carry meaning only through prose in `AGENTS.md`, and the only file-kind constraint is the hand-written "no default export except discovered files" convention. The project structure description (#148), the structure report (#156), the generated aliases and lint (#150) all classify directories through roles, so the role catalogue, its configuration and its contracts come first.

Roles live in the `project/structure` domain, which owns the whole description. The namespaces don't exist in `src/` yet: create `src/project/structure/` now (a namespace has no `index.ts`, so it adds no public entry) and add its `#project/*` subpath import by hand; generated aliases replace it later.

Decided (plan, **Roles**):

- Defaults: file roles `index.ts`, `constants.ts`, `*.d.ts`; directory roles `types/`, `utils/`, `errors/` (public), `enums/`, `ports/` (public), `adapters/` (public). The `tests` environment adds `fixtures/` and the discovered `setup.ts`; `bin` and `data` have no roles.
- Shipped off by default: `schemas/`, `components/`, `hooks/`, `contexts/`, `pages/` (discovered), `styles/`.
- `roles: { enable, disable, define }` at the top level and in each environment, top level first. `enable` and `disable` take known keys, type-safe, and apply to the defaults first; `define` applies last and may redefine a role.
- Role aliases map a directory name to a role (`helpers` read as `utils`).
- `roles: false` at the top level turns the role system off: no role is recognized, no role check or rule is produced.
- Contract fields: `file`, `accepts`, `nesting`, `roles`, `categories`, `exports`, `index`, `public`, `discovered`, `scoped` (plan, **Contracts**).
- **Scoped roles**: every role is defined once, by name, in `define`. A role with `scoped: true` is active only where a scope enables it: a structured role's `roles` list (`gql/` → `queries/`, `mutations/`, `fragments/`), or a namespace's `roles: { enable }`, which applies to its whole subtree (an app's `ui/` namespace enabling `components/`, `hooks/`, `contexts/`). The namespace option itself is declared by #148.
- A port is one type (type alias or interface) named after its file; components of a composed port stay in `types/`.
- Engrenage defines `config/`, `setup/`, `plugins/` and `operations/` in its own `engrenage.config.ts`.

## Prerequisites

None.

## Steps

1. In `src/project/structure/`, add the role model: the contract type, the default and shipped catalogues (`constants.ts`), and the resolution of the effective role set at any directory (defaults, then `enable`/`disable`, then `define`; top level, then environment, then the enclosing scopes; aliases; `false`), scoped roles active only inside a scope enabling them.
2. Declare the top-level and per-environment `roles` options in the current schemas (`src/config/config/schemas/`), with `enable`/`disable` typed by the known keys, and expose the resolved sets on the resolved config.
3. Define engrenage's own `config/`, `setup/`, `plugins/` and `operations/` roles in `engrenage.config.ts`, with the contracts the plan's **Inside a domain** section gives them.
4. Add a minimal `engrenage init` step that writes one example role definition (the project's impure-logic role) into the generated config.
5. Feed the tests root's `setup.ts` file role into Vitest's `setupFiles` in `createVitestConfig`, overridable through the Vitest options, and drop the hand-written entry from this repository's `vitest.config.ts`.

## Tests

- Resolution order: a role disabled at the top level and enabled in one environment is active only there; `define` redefines a default's contract.
- `roles: false` yields no role in any environment.
- A scoped `queries` role is active inside `gql/` and unknown elsewhere; a scoped role enabled by a namespace is active in its whole subtree only.

## Done when

Each environment's effective roles and their contracts resolve from the defaults and the configuration, engrenage's own roles included; Vitest picks up `setup.ts` by itself; the project's checks pass.
