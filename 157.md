# #157 config: workspaces with generated package files

- State: OPEN
- Labels: 🚀 — Feature

## Body

Part of #137, under #161. Read the plan, its **Workspaces**, **Aliases** and **Environments** sections, and #159, before starting.

## Context

Engrenage models one package. A typical case it must support: a Shopify app whose `extensions/*` are pnpm workspaces. Each extension carries a hand-written minimal `package.json` (`name`, `private`, `version`, `license`) and a `tsconfig.json` that only extends the root one; most hold a single `src/index.tsx`, some hold components, discovered route files and GraphQL documents; Shopify Functions have their own structure and runtime. Extensions reach the root `src/` through bundler aliases. Node subpath imports cannot cross packages (`ERR_INVALID_PACKAGE_TARGET` for `../../src/*`), so shared code goes through bundler aliases. `engrenage init` creates `pnpm-workspace.yaml` (`tools/pnpm`), but no sync target maintains it; #53 adds one for the shared settings.

Decided:

- A `workspaces` option declares globs; each maps to a name pattern with `{dir}` interpolation (`@scope/app-{dir}`), an environment and a tsconfig. One environment per glob, each workspace a domain root inside it. Workspaces needing another structure or runtime get their own glob (`extensions/functions-*` beside `extensions/action-*`).
- `engrenage sync`:
  - keeps `pnpm-workspace.yaml#packages` in line with the globs, through one `pnpm-workspace.yaml` sync target in `tools/pnpm` shared with #53's settings (whichever task lands first creates it);
  - generates each workspace's `tsconfig.json`;
  - manages these `package.json` keys and preserves every other key: `name` from the pattern, `private`, `version` and `license` from the root, and

    ```json
    "imports": { "#self/*": { "types": ["./src/*.ts", "./src/*.tsx"], "default": "./src/*" } }
    ```

- Shared code reaches workspaces only through the bundler aliases of the `src` set (#159), so a project with workspaces importing `src/` declares `src.bundled`.
- Workspaces import each other only through a declared dependency; the root `src/` never imports a workspace (resolved by #162, enforced by #150).
- Build entries (one per workspace), Vitest includes and the ESLint scope derive from the declaration.
- Engrenage never models the host platform: its CLI, TOML files, codegen configuration, locales and Wasm builds stay foreign.

## Steps

1. Declare the `workspaces` option and resolve each workspace's environment, tsconfig and name.
2. Add `packages` to the `pnpm-workspace.yaml` sync target, creating the target if it does not exist yet.
3. Add the sync targets for each workspace's `tsconfig.json` and managed `package.json` keys.
4. Derive build entries, Vitest includes and the ESLint scope from the workspaces.
5. Add the workspaces row to the import rules of `project/structure` (#162): the root `src` never imports a workspace, and workspaces import each other only through a declared dependency.

## Tests

- A fixture with two globs (`extensions/action-*`, `extensions/functions-*`): `pnpm-workspace.yaml#packages`, each `package.json` (name from `{dir}`, `#self/*` imports, a foreign key preserved) and each `tsconfig.json` match; `--check` reports drift.
- A workspace module importing `#self/…` and a `src` alias type-checks and builds through Vite.
- The resolved import rules forbid a workspace's import of another workspace that is not a declared dependency.

## Done when

Declared workspaces get their package files, `pnpm-workspace.yaml` packages and tool scopes from `engrenage sync`, and the project's checks pass.
