# #146 config: declaration helper and computed defaults

- State: CLOSED
- Labels: 🚀 — Improvement

## Body

Part of #137, under #158. Read the plan, its **Config pipeline** section, before starting.

## Context

- Valibot schemas declare `optional(…)` without defaults; `createResolvedConfig` (`src/config/utils/`) applies `raw.<option> ?? default<Option>`, and the `raw.<option> === false` branch appears 13 times.
- Option descriptions carry 51 `@default` texts, 47 kept in sync with the code by hand.
- Some defaults depend on context: the build output directory on the tsconfig, `tooling.active`, the presets.

Each domain's `config/` role should turn unknown input into validated domain data and fill every gap itself, so the domain's other code uses no defaults and the descriptions can never disagree with the code. A light helper over valibot in `foundation/options` gives every declaration that shape. It comes before the relocation of `src/` (#139), so every schema written from then on (#164, #159, …) uses it: create `src/foundation/options/` now (`foundation` is a namespace, so it adds no public entry) and add its `#foundation/*` subpath import by hand; generated aliases replace it later (#159). Declarations are migrated where they sit today; #139 moves them with their domains.

Decided:

- The helper takes the base value schema and flags replacing `optional()` wrappers: `optional`, and `disable` (accepts `false`, normalized at the boundary into an explicit disabled shape). Other flags come when a domain needs them.
- A default is `{ value }` or `{ explain, compute(context) }`. The helper appends `@default <value>` or `@default <explain>` to the description; handwritten descriptions never state defaults. Long descriptions are accepted as string arrays.
- Schemas and other keys accept callbacks receiving the context; a callback may only narrow the base schema, which gives the input type.
- The context exposes `get(section)`, reading any other section on demand (presets and global settings included). Until the layered registry (#143) provides it, the config domain (`src/config`, `project/config` after #139) implements `get` over the current resolved config.
- Presets are context for computed defaults, never a partial config merged under user input.
- A domain's resolved data is a declared interface, never `ReturnType` inference.

## Prerequisites

- #148 is closed.

## Steps

1. Implement the helper in `src/foundation/options/`, and move `src/utils/validate` and `src/config/utils/listSchemaDefaults` there, replacing them where they overlap.
2. Migrate every option declaration (each domain's `config/` role and the `project` sections) to it, moving each default out of `createResolvedConfig` into its declaration and deleting the handwritten `@default` texts.
3. Declare each domain's resolved data as an interface in its `types/`.

## Tests

- A small declaration (`tools/git`) resolves defaults and rejects invalid input; its description ends with the generated `@default`.
- A computed default (build output directory) reads the tsconfig section through `get` and explains itself in the description; `false` on a `disable` option yields the disabled shape.

## Done when

No default lives outside a declaration, no description states a default by hand, no `=== false` branch remains in the resolution, and the project's checks pass.
