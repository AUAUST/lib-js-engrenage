## Body

## Context

Boundaries and role contracts will be generated as ESLint settings from the project structure description (#150). The plan assumes eslint-plugin-boundaries (v7) can express them: it declares elements by `type` and path `pattern` with captures, and its `boundaries/dependencies` rule takes from/to selectors, with entry-point, private-element and unknown-file checks. Nothing confirms it covers the model yet. If it falls short, the enforcement approach is reviewed before #150 starts; no fallback is designed in advance.

## Prerequisites

None.

## Steps

1. On a throwaway fixture outside `main`, write the eslint-plugin-boundaries settings a generator would produce for a small project with:
   - a `src` root whose layers are `foundation < project < tools < workflows`, and a nested namespace with its own layers (`["support", "*", "ui"]`) inside a domain;
   - domains with sub-domains, one declared public, the others private;
   - default roles at several depths (`utils/`, `types/`, `ports/`, `adapters/`), file roles matched by globs (`constants.ts`, `*.d.ts`);
   - a public role (`adapters/`) imported module by module from another domain, while a private role (`utils/`) must go through `index.ts`;
   - a domain named like a role and opted out of role detection.
2. Check each rule of the plan's **Lint** table against it: a valid import passes, a violating one fails with a readable message.

## Done when

This issue records, per rule of the **Lint** table, whether eslint-plugin-boundaries expresses it and the settings that do, and lists what it cannot express.

## Findings

Prototype: a structure description, a resolver standing in for #148 (configuration first, then inference: `index.ts` → domain, known role name → role), and a generator emitting eslint-plugin-boundaries 7.4.1 settings, run on ESLint 10.13 with typescript-eslint 8.72 and eslint-import-resolver-typescript 4.4.5. Nothing changed in the repository.

### Evidence

- **Fixture**: 89 imports covering every point of the Steps (layers `foundation < project < tools < workflows`, a nested namespace `workflows/cli/commands` with `["support", "*", "ui"]`, public and private sub-domains, roles at several depths, file roles by glob, public `adapters/` versus private `utils/`, the domain `tools/typescript/types` opted out of role detection, plus environments, tests variants, data and workspaces). Each line declares its expected rule. Result: 94 expectations and 0 failures. A negative control confirms that all 89 imports resolve, so no line passes through a resolution failure.
- **Mutations**: each change to the description changes exactly the expected errors. Examples: declaring `claude` private adds a `sub-domains` error and a `tooling` error, dropping the nested `layers` removes both `layers` errors, and turning off `published` removes the 3 `tests` errors.
- **Real repository**: the generator ran read-only on a description of today's `src/` (no layers yet) over 603 files. It produced 93 elements and 155 policies in 7 ms. Linting took 2.4 s, against 0.95 s for parsing alone. It reported 454 `surfaces`, 186 `utils`, 79 `domain-content`, 32 `types`, 11 `environments` and 3 `global-roles` errors, and left `src/typescript/generated` unclassified. Most of these are the root causes of #136, for example the 98 imports of `config/types` from other domains and the 154 imports of `support/*` internals.

### Per row of the Lint table

| Row | Expressed by the plugin | Generated settings |
| --- | --- | --- |
| Environments | yes | `from`/`disallow.to` on `file.path` globs per environment pair. `tooling → src` is a disallow followed by `allow.to.element { path: <public entries>, fileInternalPath: "index.ts" }`. |
| Tests, libraries | yes | `boundaries/files` categories `test`, `test-src` and `test-dist`, built from location + suffix + variant + extension. Both rules key on `dependency.source: [pkg, pkg/**]`, because in source mode the package name resolves into `src/` through `paths`. `checkAllOrigins: true`. |
| Data, libraries | imports only | `src → data/**` disallowed. Runtime path references (`new URL("../data/…")`) are invisible to the plugin. |
| Workspaces | yes | Root `src → packages/**` disallowed. Per workspace: other workspaces disallowed, then allowed when `dependency.source` is a dependency declared in its `package.json`. pnpm symlinks resolve to real paths. |
| Global roles | yes | `from` global roles (`element.path` of root role directories, plus `file.path: "src/*"`) disallowed `to: src/**`, then allowed to global roles. |
| Layers | yes | One policy per namespace child: `from: <child>/**` disallowed `to:` the higher children. Nested namespaces work the same way. |
| Sub-domains | yes | Visibility: per private sub-domain, disallowed from `src/**`, then allowed from its parent's tree. Surfaces: disallow `src → src`, then allow domain `index.ts`, public role types, global roles, the domain's own files, and `types/` here and above. |
| `utils/`, `types/` | yes | Per role directory: disallow `src/**`, then allow its own path and the `types/` directories here and above (plus global roles for `utils/`). |
| Role contracts | `public` only | `public` is in the surfaces row. `file`, `accepts`, `nesting`, `roles`, `categories`, `index`, `exports`, `discovered`, the read-only `constants.ts`, local values in `index.ts` and runtime values in `types/` concern a file's place or content, not its imports. |
| Domain content | no | A file's existence is not a dependency. |

### What the plugin cannot express, and how the prototype covered it

- **Domain content and role contracts**: these become engrenage conventions over the resolved structure. The prototype covers `domain-content` and `role-index` with two small rules that look up `context.filename` in the resolved tree. `no-unknown-files` could catch strays, but its message is fixed and cannot say how to fix the file. Export style, `index.ts` values, `types/` values and read-only constants need AST or type-aware rules.
- **Runtime references to `data/`, and "spawn only" for `bin`**: these are not imports. Only the import half can be enforced.

### Adjustments to the approach

1. **One plugin, one rule per row.** A single `dependencies` rule has one `default`, and the last matching policy wins. Rows with their own exceptions, such as "private except public roles", therefore cannot be combined with AND inside one rule. Exposing `boundaries.rules.dependencies` under one name per row in an engrenage plugin (`structure/layers`, `structure/surfaces`, …) makes the rows independent, gives every row its own messages, and lets all rows share the `boundaries/*` settings. Verified.
2. **Exact, enumerated descriptors.** Every classified directory becomes one `partialMatch: false` descriptor, deepest first. With exact patterns the plugin computes no `parents`, so the `relationship`/`parent` selectors and captures are unusable. The generator knows the tree and enumerates paths instead. Generic partial patterns with captures would give parents, but they cannot honour opt-outs: a role-name pattern matches at the shortest suffix before any longer exact pattern is tried. Descriptors therefore follow the filesystem when the config loads.
3. **Every environment file must be known.** A source file whose element is unknown is never checked, even when path policies match it. Environment files outside the environment's directory, such as root `*.config.ts` files, get a `boundaries/files` category.
4. **`boundaries/root-path` must be set.** It defaults to the process working directory, not to ESLint's `cwd`.
5. **The resolver needs a precedence rule:** only an exact domain declaration opts a role-named directory out, and glob declarations (`"tools/*": { public: true }`) only add metadata. Otherwise `"*"` turns `src/types` into a domain. Today `src/config` needs that exact opt-out, because it is named like the engrenage-defined `config/` role. After #139 it sits under the `project` namespace and needs none.
6. Messages are custom per policy, with `{{to.file.path}}`, and `boundaries/legacy-templates: false`.

Not prototyped, but expressible the same way: the app variants (tests through `#…`, `#data`, `tooling →` declared domain surfaces) and the `config/` role row.

### Decisions

The questions raised here are settled and written into the plan (#137, **Environments**, **Tests (libraries)**, **Inside a domain**, **Lint**):

1. Sub-domains, at any depth and through nested namespaces, import their ancestors' roles directly, within their own role's row; an ancestor reaches a sub-domain only through its `index.ts`.
2. `utils/` imports `utils/`, `types/` and `constants.ts` here and above, global roles, and the `index.ts` of the domains its layer allows, type-only; nothing else.
3. `types/` imports the `index.ts` of the domains its layer allows, type-only.
4. Tests import `scripts`.
5. `x.test.src.ts` imports `bin` modules; other variants only spawn it.

The adjustments to the approach are written into the plan's **Enforcement** and into #150; the resolver precedence (adjustment 5) is implemented by #148. The import contract is resolved once in `project/structure` (#162), which #150 and #151 consume. Tests directories are classified by the tests layout (#164).
