## Goal

`src/` has no layers: `config` is both hub and tool, one aggregate `ResolvedConfig` is the only contract, concerns serving several tools have no owner. Target: namespaces of domains ordered by layers, roles with contracts, contract domains with ports and adapters, a layered configuration registry, generated code placed like handwritten code, workspaces, a suite testing the built package, and one project structure description generating aliases, the structure report, lint boundaries and agent guidance. The same model fits engrenage, toolkit and apps.

## Model

| Noun            | What it is                                                                                         | Declared where                                       |
| --------------- | -------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| **Environment** | Runtime context with its own directories and import rights (`src`, `bin`, `scripts`, `tests`, `data`, `tooling`) | config                                  |
| **Namespace**   | Grouping directory: no `index.ts`, no roles; holds domains and namespaces; carries its children's **layers** | `structure.namespaces` or a preset         |
| **Layer**       | Order of a namespace's children, lowest first, `*` for every child not listed (`["support", "*", "ui"]`) | the namespace's `layers`                     |
| **Domain**      | Any directory neither role nor namespace, recursively; one concern, one surface (`index.ts`)       | implicit; metadata in `structure.domains`            |
| **Role**        | Directory or file name with a fixed meaning and contract, valid at any depth                      | `roleCatalogue` (`src/project/structure/constants.ts`), presets, project `roles` |

- Classification, highest priority first: project configuration, preset defaults, filesystem inference (a domain has `index.ts`, a namespace never does, a role is a known role name). Every default is configurable; whatever is not declared is inferred. Everything derives from it: lint, agent guidance, the structure report, entries, aliases, lint and format scope.
- A child imports global roles, lower layers and its own layer's peers through their `index.ts`, never a higher layer. Children of a namespace without `layers` are unordered peers; layers are never inferred from imports. Layers prevent cycles, so no tool checks them.
- A domain does not order its sub-domains; a namespace is inserted for that, at any depth.
- Children of a namespace are never roles, except at an environment root, which also holds the global roles. Only an exact `domains` path or an `optOut` entry turns a role-named directory into a domain; a glob in `domains` only adds metadata.
- Strictness per environment: `strict` (default) requires every directory classified; `loose` treats unclassified directories as plain domains (as mirrors in `tests`, #164) and checks only recognized roles. `engrenage structure` (#156) reports and checks it, files outside any role included.

## Environments

| from ↓ / to → | `src` public                    | `src` internal (`#…`)                      | `bin`                                          | `scripts` | `data`                                        |
| ------------- | ------------------------------- | ------------------------------------------ | ---------------------------------------------- | --------- | --------------------------------------------- |
| `src`         | §Imports                        | §Imports                                   | never                                          | never     | library: at runtime through the public specifier (`foundation/data`); app: `#data/…` |
| `bin`         | yes                             | yes                                        | own command tree                               | never     | never directly                                |
| `scripts`     | yes                             | yes                                        | never                                          | own       | read and write by path (generated files)      |
| `tests`       | library: package name only (`x.test.ts`) | library: `x.test.src.ts` only; app: always | spawn; library: imports from `x.test.src.ts` only; app: always | yes | library: public specifier; app: `#data/…` |
| `tooling`     | library: public entries only    | app: declared domain surfaces              | never                                          | never     | never                                         |

- Other environments never import `tests`. `bin` holds thin discovered commands, no roles. `scripts` holds generators with their inputs beside them. `tests` is one configurable root (`resources/tests`), never colocated, keyed by tested environment (#164). `data` has no roles and no structure lint; a library's `data.exports` defines its layout. `tooling` is the root config files plus `tooling/`, imported through `#tooling/…`: `src` roles, no layers, one domain per tool (#160).

### Library versus app

The **published** trait (#153), which the `library` preset resolves to, carries the difference; rules read the trait, never the preset.

| Concern            | Library (published)                                   | App                          |
| ------------------ | ----------------------------------------------------- | ---------------------------- |
| Dist testing       | source and dist modes, test variants                  | none: no dist mode or tsconfig |
| Tests import `src` | `x.test.ts` by package name; `x.test.src.ts` by `#…`  | `#…` aliases                 |
| `src` → `data`     | runtime only, through the public specifier            | static, `#data/…`            |
| `#data` alias      | never                                                 | on by default                |
| `tooling` → `src`  | public entries only                                   | declared domain surfaces     |

| Test file        | Runs in          | Imports                                                                  |
| ---------------- | ---------------- | ------------------------------------------------------------------------ |
| `x.test.ts`      | source and dist  | public specifiers, `#tests/…`, `scripts`                                 |
| `x.test.src.ts`  | source only      | internals through `#…`, `bin` modules, `scripts`; never the package name |
| `x.test.dist.ts` | dist only        | public specifiers, `scripts`; may reach dist-only artefacts              |

- A test importing a script that reaches internals is `x.test.src.ts`; the dist guard fails it otherwise.
- Whatever is public is tested through its public specifier.

## `src/` of engrenage

```
src/                       layers: foundation < project < tools < workflows
├─ index.ts  constants.ts  types/  utils/        global roles; utils stay pure
├─ foundation/             no project knowledge: filesystem, processes, data, json, blocks, options
├─ project/                tool-agnostic models and contracts:
│                          config, structure, environments, presets, package, tsconfig, baseline,
│                          build (ports, entries, output, target, formats, clean policy), formatting (ports)
├─ tools/                  one domain per external tool, holding its adapters:
│                          typescript, eslint, prettier, pnpm, tsdown, vite, vitest,
│                          changesets, git, github, vscode, agents/{claude,codex}
└─ workflows/              composition: registry, init, sync, cli
```

| from ↓ / to → | global roles | `foundation` | `project` | `tools`               | `workflows` |
| ------------- | ------------ | ------------ | --------- | --------------------- | ----------- |
| `foundation`  | ✓            | peers        | ✗         | ✗                     | ✗           |
| `project`     | ✓            | ✓            | peers     | ✗                     | ✗           |
| `tools`       | ✓            | ✓            | ✓         | peers (vitest → vite) | ✗           |
| `workflows`   | ✓            | ✓            | ✓         | ✓                     | peers       |

- Global roles import only each other.
- Visibility: internal unless declared public. Public: every `tools` domain (with `agents/claude`, `agents/codex`) and `project/{config,package,baseline,formatting}`; specifiers derive from the declaration (#154).

## Inside a domain

```
tools/tsdown/
├─ index.ts        surface
├─ constants.ts    deeply read-only constants, hard-coded data included
├─ config/         pure option declarations (engrenage-defined role)
├─ setup/          init steps and sync targets only (engrenage-defined role)
├─ plugins/        the tool's own plugins, one per module (engrenage-defined role)
├─ operations/     impure logic and definers (engrenage-defined role)
├─ adapters/       implementations of other domains' ports (public role)
├─ utils/          pure, contained functions
├─ types/          types only
└─ <sub-domain>/   same rules; private unless declared public
```

| Role        | May import                                                                                                                       |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `types/`    | `types/` here and above; type-only, the `index.ts` of domains its layer allows                                                   |
| `utils/`    | `utils/`, `types/`, `constants.ts` here and above, global roles; type-only, the `index.ts` of domains its layer allows           |
| `config/`   | `foundation/options`, lower-layer surfaces, `types/`, `utils/`, `constants.ts`                                                   |
| other roles | anything the domain's layer allows                                                                                               |

- "Here and above": the domain and its ancestors, through nested namespaces.
- A sub-domain imports its ancestors' roles directly, within its own role's row; an ancestor reaches a sub-domain only through its `index.ts`.
- A public role (`adapters/`, `ports/`, `errors/`) is importable module by module, the one exception to "through `index.ts`".
- A domain holds only roles, sub-domains and namespaces.
- The home of impure logic is each project's choice; engrenage defines `operations/`, enough for its volume.

## Config pipeline

```
foundation/options      declare(), flags, computed defaults           no project knowledge
        ▲
project/config          raw input loaded once per root (c12), memoized;
                        project sections resolved lazily through get(section); public loadConfig(root)
        ▲
tools/<tool>/config     declares its section
tools/<tool>/operations define<Tool>Config() = raw → own section + get('build', 'baseline', …)
        ▲
workflows/registry      every section, eager validation, composed Config type, full loadConfig(root)
```

- No module imports a higher layer. A cycle between sections fails with its path.
- Unknown keys fail under eager validation (CLI, `--check`), ignored by a partial resolution.
- A domain exports an environment sub-schema under its name (`tsconfig`, `exports`); the registry composes each environment's schema from them.

## Decisions

- A concern gets a contract domain only when two engines exist or a consumer needs the intent without the engine: `build` and `formatting` qualify; lint, typecheck and install do not.
- Contract domains declare interfaces in `ports/`; tool domains implement them in `adapters/`; `workflows` injects adapters. Tools engrenage needs itself get no namespace: requiredness is dependency metadata, and a capability it needs goes through a port.
- The tsconfig model, package layout and baseline sit in `project`, below every tool; `tools/typescript` consumes the tsconfig model like ESLint, tsdown and Vitest.
- A role is on by default only when its name serves no other purpose, conflicts with no other role and means the same in every environment; the catalogue grows when a preset needs a role.
- A domain owns its capabilities' logic; `workflows/cli` turns them into commands; `bin/` stays thin.
- One verb per module kind: `create…Step` for init steps, `sync…` for sync targets only, `generate…` for generators, `define…Config` for definers.
- Library-only behavior reads the `published` trait; until #153 adds it, read the `library` preset with a `@debt` marker naming the trait.
- With the role system off (`roles: false`), no role or boundary rule is resolved or generated, and the rest of engrenage works unchanged.

## Done when

Tests run against the built package, `src/` follows the namespaces, domains and roles above, the configuration is the layered registry in its final shape, and aliases, the structure report, lint boundaries and the agent project map derive from the project structure description.
