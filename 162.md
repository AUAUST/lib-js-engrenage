# #162 structure: import rules resolved from the project structure

- State: OPEN
- Labels: 🚀 — Feature

## Body

Part of #137, under #158. Read the plan, its **Environments**, **Inside a domain**, **Roles** (`public`) and **Lint** sections, and #138's findings, before starting.

## Context

The import contract (plan §2, §4 and the **Lint** table) has two consumers: lint generated as eslint-plugin-boundaries settings (#150) and the generated agent project map (#151). Derived in each, the two could disagree. The resolved structure (#148, `resolveEnvironmentStructure` in `src/project/structure/`, exposed as the resolved config's `structure`) already knows every environment, namespace, layer, domain, visibility and role, so the contract is resolved once, tool-agnostic, in `project/structure`, and both consumers translate it.

Decided:

- The import rules are resolved in `src/project/structure/` from the resolved structure and the environments, per row of the plan's **Lint** table that concerns imports: environments, tests (libraries), data (libraries), global roles, layers, sub-domains (visibility, surfaces, ancestors' roles, public roles), `utils/` and `types/`, `config/`. The workspaces row is added by #157.
- Each rule names its source (an environment, element or test variant), its targets (an element, an element's `index.ts`, its modules, a file category), whether it allows or forbids, whether only type-only imports qualify, and the reason in words, from which #150 writes lint messages and #151 writes the map. Nothing in it is specific to ESLint or to a glob syntax.
- The contract as the plan states it, exceptions included: sub-domains import their ancestors' roles within their own role's row, and an ancestor reaches a sub-domain only through its `index.ts`; `utils/` imports `utils/`, `types/` and `constants.ts` here and above, global roles, and other domains' `index.ts` type-only as their layer allows; `types/` imports `types/` here and above and other domains' `index.ts` type-only as their layer allows; tests import `scripts`; `x.test.src.ts` imports `bin` modules.
- Runtime references to `data/` and `bin` being spawned are part of the rules with their reason, flagged as not enforceable by import analysis, so #151 still states them and #150 skips them.
- Library-only rules read the `library` preset until the `published` trait exists (#153); mark the check with a `@debt` marker naming the trait.
- With the role system off (`roles: false`), no role or boundary rule is resolved.
- The rules are exposed beside the resolved structure on the resolved config, resolved on first read.

## Prerequisites

## Steps

1. Add the rule types to `src/project/structure/types/` and their resolution from the resolved structure and environments.
2. Expose the resolved rules on the resolved config, beside `structure`.

## Tests

- A fixture with layers and sub-domains: an import into a higher layer is forbidden; a sub-domain's import of its parent's `utils/` is allowed; a `utils/` module's type-only import of another domain's `index.ts` is allowed, its runtime import is not.
- The same fixture as a library and as an app: `x.test.ts` may import only the package name in the library, `#…` aliases in the app.

## Done when

Every import rule of the plan's **Lint** table, except the workspaces row, resolves from the structure with its reason, and the project's checks pass.
