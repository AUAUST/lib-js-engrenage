# #162 structure: import rules resolved from the project structure

- State: OPEN
- Labels: 🚀 — Feature

## Body

#137 › #158 · §Imports: rows resolved once, tool-agnostic · §Inside a domain: role rows and exceptions · §Library versus app

## Context

Lint (#150) and the project map (#151) both need the import contract; derived in each, they could disagree. Decided: `src/project/structure/` resolves it once from the resolved structure (`resolveEnvironmentStructure`, the resolved config's `structure`) and the environments, and exposes it beside `structure`, resolved on first read.

## Steps

1. Add the rule types to `src/project/structure/types/`: each rule names its source (environment, element or test variant), its targets (an element, its `index.ts`, its modules, a file category), allow or forbid, whether only type-only imports qualify, and its reason in words. Nothing specific to ESLint or to a glob syntax.
2. Resolve the rules of every import row of §Imports except workspaces (#157), with the sub-domain, public-role, `utils/` and `types/` exceptions of §Inside a domain and the `tests` and `x.test.src.ts` rights of §Environments.
3. Include runtime references to `data/` and spawning `bin`, flagged as not enforceable by import analysis, so #151 states them and #150 skips them.
4. Expose the rules on the resolved config beside `structure`.

## Tests

- A fixture with layers and sub-domains: an import into a higher layer is forbidden; a sub-domain's import of its parent's `utils/` is allowed; a `utils/` module's type-only import of another domain's `index.ts` is allowed, its runtime import is not.
- The same fixture as a library and as an app: `x.test.ts` may import only the package name in the library, `#…` aliases in the app.
