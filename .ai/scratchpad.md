# Scratchpad

- a worker should be instructed to "commit every time it reaches a start that works and that can be built upon, unless the work is done in which case commit only in the main session". wording to be settled, but the idea is that a worker working on a relatively large task should commit every time it made several changes that are expected to work; i.e. where we had checkpoints earlier. helps legibility and resumability on budget stops.

- while enforced by the structure checks, the worker should not be told to "place freely"; it should be told to respect the project architecture and report a file that doesn't have a proper owner. domains, namespaces, workspaces, boundaries, layers, roles are all there to ensure the codebase remains maintainable; reuse, placement, helper aren't free, they must strictly follow the project convention and raise when a clean architecture cannot be reached. The worker is the guarantor of good architectural decisions. The planner sets the overall goal, the worker ensures the system allows its implementation and stops when the architecture doesn't have a home for the feature. We'd rather pause and cleanup the architecture than implement and accept increasing debt.

- we'll want to start grouping all metalbrain and nexus logic into namespaces like we started with batiment, so that further implementation gets placed correctly from the begining

- the planner agent should be tought to understand the general project structure and boundaries: while it must not care about implementation details, it must have the necessary awareness of the project structure to know that X or Y will live in a given domain or namespace, will be a role, ...; if the planner just vibe full plans disregarding any technical fact, it'll be messy on walks. ideally, i would come with simple needs to the planner: "I want X to be implemented". From there, the planner, using its overall knowledge of the architecture, understand it's CLI, hook, feature, ... and already tries to see where it goes in the architecture. this way, a planning phase already catches lacks in the architecture so that a worker doesn't hit an architectural stop. the /shape should share that architectural knowledge for the same reasons

- the instruction writing skill should always consider the mechanical approach, and weigh it against replacement or addition. for example, given a constraint we want to enforce, it must infer whether this is a mechanical thing that is worth considering coding as a guard. then, when a mechanical check exists, it must weigh whether prose on top of it is still beneficial: an agent receiving correct directions and implementing correctly is usually better than a whole implementation that breaks at the boundary because no prose existed. as such, a balance between full prose, no prose, specific or general prose against the mechanical checks must be considered as part of the general instructions writing.

- because main sessions are locked with context bloat from the app and Haiku is far cheaper, I would be interested in checking whether starting haiku main sessions that strictly just forward tasks verbatim to a subagent is of any gain or pointless indirection.

- the default K for walks is 1, sequential. parallelisation is opt-in; this includes unrelated work in the main checkout.

- ensure that agents dispatching workers as "free briefs" mimmick the content of an issue: gives a short context, describes Done when and the necessary facts from the main session.

- consider an `architecture` skill + `architect` agent: it would have the role of a consultant that planners can invoke or used in the main session to prepare the goal of a plan. it must be roughly in between an analyser, a planner in both outer and inner modes and a worker. its role is to understand the dependencies, directions and boundaries and help design clear archictecture. it would be relatively rarely used and only when planning refactoring or new projects, its role being to anticipate relationships, the correct layers and split, ... in this codebase for example, it should've catched the metalbrain split in advance: "engrenage's scope is tooling orchestration; are you sure you want to include all the agent instructions, github layer, planning layers in there?". i.e. it'd be the guarantor of good practices, maintainability and ownership. when something seems like it's leaking outside the scope but a switch is too costly or genuinely not worth it yet, it would suggest preparing a split by already grouping something in its own namespace and entries so that it's only imported through a known surface and a later switch becomes quite more mechanical and costly. in our case now, it could thus understand how to prepare #684 correctly. exact role, scope, skills, responsibilities, dispatch strategy and skill's approach tbd. it should also ideally not be strictly only scoped to structure, namespaces and domains. it should also understand general project architecture (i.e. in interscript shopify, the winning layout for extensions, the theme, admin UI, ...) and general tooling: how to properly lint, avoid dead code, ...; a general "code quality at the surface level". i.e. it doesn't bother with implementation design, but with contracts, direction, ownership, maintainability, roles, dependencies, ...
