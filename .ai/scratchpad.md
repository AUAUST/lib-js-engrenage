# Scratchpad

- i would be interested in having @auaust/codegen provide actually code-based generation. The very same way we have .domain.json in the structure to provide facts in place rather than declare structure in a config and be guaranteed to drift, I could very well see "barrel metafiles similar to domains and namepsaces also checked against schemas to describe how barrels are generated. right now, it's always through `@barrel` statements but I have trouble with magic strings. It's hard to find the logic behind, and it means having unchecked fact that generate code. Thus, having maybe `.barrel.json` could provide the facts from a schema so each key is known and validated with a description. And the code-based approach would be similar though even more polyvalent by having, say, `.barrel.codegen.ts`, that exports a barrel manifest. it would be in a new tsconfig.codegen.ts only, not accessible to any other tsconfig, would not be importable by code and define how a given barrel behaves. This way, instead of having magic strings, we could have functions that can export known values; it would be part of the codegen split.

- the linting setup must rather urgently be improved. toolkit usage not enforced at all. global rules are too constraining. the switch to oxlint must still be validated (and, ideally, measured: attempt a drop in replacement, see what works as is and breaks, measure what works, align the same rules to eslint, run the same checks, compare). whichever linter, we want to set the two most important connectors: hooking rules to 'structural items', i.e. rules per workspace, namespace, domain or role individually, and rule extensions. in the end, linting already provides the extension by just creating more rules from different projects. the extension part of engrenage should work by exposing the tooling so that toolkit can create simple rules reusing engrenage's own tooling, and provide default rules that engrenage adds appropriately. all the boundary checks should be provided the same way by batiment, which on top of its core should have the adapters layer that provides wrappers; i.e. there's the abstract structure tree, the ESM adapter that understands graphs as well, and the lint rules built from the resolved facts

- `@auaust/machinery` library: it would be to "systems" what `@auaust/toolkit` is to code. abstractions and helpers over common operations like filesystem read and writes, parsers (markdown, shell, ...) so that all others projects can rely on the same tools without having to review all of them all over again. Things it could contain:
  - a `path` module that combines `node:path`, `minimatch` and common helpers such as `resolveWithin`

Philosophy: it should implement most behaviours through `abstracts`. Instead of providing implementations directly, it would expose abstracts and concretes (ports and adapters) that define capabilities. It would then allow to switch the implementation so that the same code runs in different environments (cf. codegen below). It should not become a whole service container architecture but rather contain a few modular tools that help with the common operations that support such pattern. Going into a service container pattern means we start creating massive context objects and every last tool requires dozens of unrelated services to be instanciated for the context object to pass the type checks. Instead, it should ideally enforce modularity and minimalism by design; i.e. the very construction of these swappable implementation must make it easier to use granular requirements than magic objects. -> SOLID, YAGNI
It should also be extensible: any pattern the library provides (i.e. how each abstract is defined and implemented) should be user facing so they can do the same.
Any operation should live behind an abstract: path operations, filesystem abstractions, ... are all decoupled from the node internals. Making them browser-compatible isn't a polyfill but an implementation swap. (strategy pattern ish)

- codegen must provide a shared filesystem port that allows easily performing ops regardless of where it gets written. typically, metalbrain's records would take it in as of right now, a test that writes or reads files would be easily mocked, theoretically it could even be used to implement isomorphic code that for example writes to the local storage in a browser. whether it's part of codegen, nexus or a new `@auaust/machinery` library tbd

- should be considered: codegen and machinery as one library?

- lint should flag modules that include too many helpers. it's hard to find a magic number on that; 1 or 2 private helpers is mostly fine, 10 is rarely a good sign. the exacct rule behind tbd, but modules that grow vertically aren't that nice. we're already limiting the overall module length, which is good, but that metric alone leaves behind a few weirdies.

- a debugger must be instructed to always run a full CI suite before reporting, so it catches any existing typecheck, lint, test or other reported error; based on the context and its instructions, it decides whether to fix directly or to report, as it already does.

- a writer, even dispatched at low effort for a mechanical change, should be asked to review the files it reads. not every dispatch must require loading all instructions, but even when the brief seems extremely fixed and set, it should reason over it, find how agents could misbehave. i.e. even when its dispatcher requires one tiny mechanical change, it must do its normal job. a scoped and specific request limits the instructions loaded, not the thinking phase asking how the instructions could go wrong or bias agents in the wrong direction. this also includes the rest of the file, not strictly the matched location. each dispatch being an opportunity to catch misalignment, outdated facts, conflicts, ambiguities, examples and enumerations is a win. it should still report rather than edit on a whim.
